# Register throughput API

`flops_ceiling::registers` measures BF16, FP8 E4M3 and FP4 tensor throughput,
and full FP32 scalar FMA throughput, on
DGX Spark / GB10 (SM121). Rust generates PTX, owns the CUDA driver resources,
validates checksums, and measures GPU time. There is no C++ wrapper or CUDA C++
kernel. The device code is explicit PTX generated by Rust, rather than a
Rust-language kernel compiled through cuTile.

## Use the API

```rust,no_run
use flops_ceiling::registers::{benchmark, Config, Format, Sparsity};

let result = benchmark(&Config {
    format: Format::Nvfp4,
    sparsity: Sparsity::Dense,
    a_value: 1.5,
    b_value: 2.0,
    scale_a: 1.0,
    scale_b: 0.5,
    accumulator_start: 2.5,
    accumulator_step: 0.25,
    warmup_launches: 100,
    trials: 10,
    ..Default::default()
})?;

println!("mean {:.2}, best {:.2} TFLOPS",
    result.tflops.mean, result.tflops.max);
# Ok::<(), flops_ceiling::Error>(())
```

The synchronous call restores the calling thread's CUDA context. Serialize
benchmark calls to avoid measuring GPU contention. `kernel_ptx(&config)` returns
the generated source without initializing CUDA. An executable example is
[`examples/register_ceiling.rs`](../examples/register_ceiling.rs).
`config.validate()` checks the configuration and `config.expected_checksum()`
computes the timed kernel's expected FP32 checksum without initializing CUDA.
For Nsight, use `benchmark_with_profiler_range(&config)` or CLI `--profile-range`;
see [profiling controls and available measurements](profiling.md).

`Format::{Bf16, Fp8, Fp32, Nvfp4, Mxfp4}` selects arithmetic. The previous
`ScaleFormat` name remains a type alias, so existing FP4 callers still compile.

## Build and run

Use the same Rust/CUDA environment as the [GEMM API](benchmarking.md). This API
also links the CUDA driver library, `libcuda`. Driver JIT compilation targets
PTX 9.0 / `sm_121a`; CUDA 13.0 and driver 580.173.02 were used for the recorded
runs. The library rejects devices other than SM121.

```sh
cargo build --release --locked --bin register-ceiling
cargo run --release --locked --bin register-ceiling -- \
  --warmup 10 --rounds 5 --output artifacts/registers-short

# All new types; defaults to dense + sparse for BF16/FP8, dense only for FP32.
target/release/register-ceiling --formats bf16,fp8,fp32 --warmup 100 \
  --rounds 3 --trials 5 --launches-per-trial 100 \
  --output artifacts/registers-new-types

# Longer batches; same arithmetic kernel and loop count.
target/release/register-ceiling --formats nvfp4 --warmup 100 \
  --rounds 3 --trials 10 --launches-per-trial 1000 \
  --output artifacts/registers-longer

# Generate auditable PTX without running a GPU kernel.
target/release/register-ceiling --emit-ptx-only --output artifacts/registers-ptx

# Compare A=1, B=1 against A=1, B=2, keeping both scales at 1.
target/release/register-ceiling --formats nvfp4 --b-values 1,2 \
  --rounds 5 --output artifacts/registers-b-comparison

# Sweep signed/fractional operands and block scales with custom initialization.
target/release/register-ceiling --formats nvfp4 --a-values=-1.5,0.5 \
  --b-values 2,3 --scale-a-values 1,1.5 --scale-b-values 0.5 \
  --accumulator-start 2.5 --accumulator-step 0.25 \
  --accumulators 16 --threads 128 --blocks-per-sm 8 --iterations 700 \
  --warmup 100 --trials 10 --launches-per-trial 1 --rounds 3 \
  --output artifacts/registers-parameters
```

Defaults: MXFP4 and NVFP4, both sparsities, 16 independent MMA chains per
warp (FP32 uses 16 scalar FMA chains per thread), 128 threads per block, a grid of 8×SM-count blocks, 700 loop iterations,
10 warmup launches, and ten trials of one launch. Odd-numbered rounds reverse
the order of all cases. The grid multiplier does not specify
the number of simultaneously resident blocks.

## Parameters

| Rust `Config` field | CLI option | Default |
| --- | --- | --- |
| `a_value`, `b_value` | `--a-values`, `--b-values` | 1, 1 |
| `scale_a`, `scale_b` | `--scale-a-values`, `--scale-b-values` | 1, 1 |
| `accumulator_start`, `accumulator_step` | `--accumulator-start`, `--accumulator-step` | 0, 1 |
| `accumulators` | `--accumulators` | 16 MMA chains (four outputs/thread) or 16 FP32 FMA chains/thread |
| `threads_per_block` | `--threads` | 128 |
| `blocks_per_sm` | `--blocks-per-sm` | 8 (grid multiplier) |
| `iterations` | `--iterations` | 700 |
| `warmup_launches` | `--warmup` | 10 |
| `trials`, `launches_per_trial` | `--trials`, `--launches-per-trial` | 10, 1 |
| `device` | `--device` | 0 |
| `format` | `--formats` | API: NVFP4; CLI: MXFP4 and NVFP4 |
| `sparsity` | `--sparsities` | API: dense; CLI: supported modes per format |

The CLI takes comma-separated lists for formats, sparsities, A, B and both
scales, and runs their Cartesian product. Every scale must be valid for each
selected format. `--rounds` repeats the sweep (default 1). `--output` selects a
new artifact directory; `--emit-ptx-only` generates source without CUDA.

For FP4, A and B are uniform E2M1 values: **0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6**.
Scales must be positive and exactly representable: NVFP4 uses UE4M3 values from
1/512 through 448; MXFP4 uses powers of two from 2^-127 through 2^127. Unsupported
values are rejected, never silently rounded. Combinations that produce a
nonzero subnormal FP32 product, a nonfinite or inexact FP32 MMA increment,
or a nonfinite reference checksum are rejected.

BF16 and FP8 require finite values exactly representable in BF16 or E4M3.
FP32 accepts finite `f32` operands, including values such as `1.0001`; its CPU
reference uses fused `mul_add` rounding. All three require unit scales. Explicit
FP32 sparse requests are rejected. For Tensor Core formats, the normal-product
and exact-increment restrictions above still apply, using the dense K below.

Scalar accumulator `j` starts at `accumulator_start + j * accumulator_step`,
rounded to FP32. The step must be nonzero and all starting values must be
finite and distinct, keeping independent recurrence chains intact. Tensor
operands, scales and initialization are specialized into PTX before timing.
FP32 operands are uploaded before measurement and loaded once per kernel into
registers, preventing the compiler from replacing constant-input FMA with adds. Changing
their numeric values does not change the FLOP formula.

Accumulator count is 1–32, threads must be a positive multiple of 32 up to
1024, and iterations are 1–65536. Other counts are positive. Device and kernel
resource limits are also checked. Tensor instructions fix M=16, N=8, a
format-dependent K (below), a 32-thread warp and four scalar outputs per chain
per thread. FP32 has one output per scalar FMA chain. These dimensions and
the fixed sparse metadata are not tuning knobs.

Each invocation requires a new directory and writes the manifest, per-trial
JSON, CSV summaries, exact PTX, and available Cargo lock. Failures are recorded
in `errors.json` and cause a nonzero exit. Records include the binary hash,
available revision, device/driver details, register usage, checksums and GPU
telemetry before and after each case. A single trial is preliminary.
Manifest and result schema version 3 include every input and scale; stable
case IDs map manifest configurations to PTX filenames and results. Older
records default missing input/scale/initialization fields to their old values.

## Formats and FLOP counts

| Mode | Data / scales | Dense instruction | Sparse instruction |
| --- | --- | --- | --- |
| `bf16` | BF16 / unscaled | `m16n8k16` | `m16n8k32` |
| `fp8` | E4M3 / unscaled | `m16n8k32` | `m16n8k64` |
| `fp32` | Full FP32 / unscaled | `fma.rn.f32` | Unsupported |
| `nvfp4` | E2M1 / UE4M3, block 16, `scale_vec::4X` | `m16n8k64` | `m16n8k128` |
| `mxfp4` | E2M1 / UE8M0, block 32, `scale_vec::2X` | `m16n8k64` | `m16n8k128` |

The FP4 modes use the packed `kind::mxf4nvf4` instruction family. `mxfp4` matches the
scale format of the community peak benchmark. Sparse mode uses a valid fixed
2:4 pattern in A. Each output receives dense-K nonzero products in either mode.

Count one multiply and one add as two FLOPs. Per launch:

```text
warps = grid_blocks × threads_per_block / 32
MMA instructions = warps × iterations × accumulators
FLOPs = MMA instructions × 2 × 16 × 8 × K
```

K follows the tensor instruction table. **Sparse TFLOPS is dense-equivalent:**
it counts the implicit zero terms; the nonzero arithmetic count is half that
figure. FP32 instead counts `threads × iterations × accumulators × 2`.
`flops_per_warp_instruction` is 64 for FP32, versus `2*16*8*K` for MMA;
`instruction` identifies the engine. The legacy `flops_per_warp_mma` is zero
for FP32 and unchanged for Tensor Core formats.

Reusing the same small operands measures repeated instruction work,
not the useful work of a large matrix multiplication.

## Timing and validation

Compilation, resource setup, checksum probes, warmup and telemetry are outside
the CUDA-event intervals. Timing includes kernel initialization, loop control,
all arithmetic instructions, a checksum reduction, and one four-byte global store per
thread. The hot loop contains no operand-memory loads. Multiple launches per
trial also include any gaps between launches.

Tensor operands and scales are baked into each entry point. FP32 loads its two
operands before the arithmetic loop; those initial loads are included in timing. Accumulators start at
distinct values to retain independent recurrence chains. Every accumulator
contributes to the stored checksum. The benchmark checks all threads after
configured-input, scale-two (FP4) or input-two (unscaled), and negative-input probes, and checks the final timed
output. These are instruction sanity checks on uniform patterns, not a general
GEMM correctness test. The API rejects kernels reporting local-memory use or
shared memory. Recorded disassembly additionally checks the hot loop for memory
instructions; register usage alone would not detect constant-memory reloads.

Each MMA adds `dense_K * A * B * scale_a * scale_b` to each scalar accumulator.
Each FP32 FMA uses `A.mul_add(B, accumulator)`, rounded once.
The CPU reference repeats FP32 accumulation and checksum reduction in order;
a closed-form sum can differ once rounding occurs. Every configuration must
pass the GPU checksum comparison before a result is reported.
This is a **strict reference check**. The [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#warp-level-matrix-instructions-mma)
leaves MMA accumulation order and rounding unspecified. Widely separated scale
and initial-value magnitudes can therefore be representable yet fail this
check. Such configurations return an error and no throughput result; the API
does not loosen the tolerance to accept them. Adjust the scales or initialization
if this occurs. `Config::validate()` checks encodings and the CPU reference;
only running `benchmark()` checks agreement with the GPU.
The [final report](final-report.md#flop-counting-and-correctness) summarizes
validation evidence and points to the external experiment archive.

For FP4, with default A=1, scales=1, initialization j=0..63, 16 accumulators and 700
iterations, each thread's checksum is **2,869,216**
for B=1 and **5,736,416** for B=2. Each scalar accumulator starts at its index
j=0..63 and gains `64 * B` per iteration. The resulting checksum is
`64 * 700 * 64 * B + 2016` in both dense and sparse modes. Result records retain
the expected checksum, observed minimum/maximum, checked thread count and error.

Report the mean, variability and best trial separately. Thermal state, clocks,
launch geometry, accumulator count and timing length affect the result. This
API's rates belong alongside, rather than in, the full-GEMM throughput table.

## References

The independent Rust implementation follows the measurement idea in
[`secYOUre/nvfp4bench`](https://github.com/secYOUre/nvfp4bench/blob/main/src/peak_mma.cu).
It adds strict NVFP4 scaling, checked checksum stores, configurable repetitions,
and structured results. NVIDIA documents the underlying instructions in the
[PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#warp-level-matrix-instructions-mma).
See the [final report](final-report.md) for measured results, limitations and
external evidence locations. Register instruction throughput and full GEMM
throughput must remain separate when comparing results.
